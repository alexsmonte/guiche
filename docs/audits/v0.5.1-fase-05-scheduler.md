# Guichê v0.5.1 — Fase 05 / Durable Scheduler

## Escopo

Esta fase implementa persistência e coordenação de eventos agendados.

Ela não executa handlers de negócio.

```text
ScheduledEvent
      ↓
JsonScheduledEventStore
      ↓
Scheduler
      ↓
claim / lease / reclaim
```

## Persistência

Backend P0:

```text
storage definido pela aplicação
scheduled-events.json
scheduled-events.lock
```

A escrita usa:

```text
LOCK_EX
temp file
fflush/fsync quando disponível
rename atômico
```

## Claim

Somente eventos:

- `pending` vencidos; ou
- `claimed` com lease expirado

podem ser reivindicados.

O claim é atômico sob lock global do store local.

## Lease fencing token

Cada claim gera:

```text
lease_owner
lease_token
lease_until
claim_count
```

O `lease_token` é o fencing token.

Se o lease expirar e outro worker fizer reclaim, um novo token é emitido. O token antigo não pode:

- renovar lease;
- concluir o evento.

## Dedupe

`dedupe_key` fornecida pela aplicação não é persistida em claro.

Persistimos somente:

```text
sha256(dedupe_key)
```

Reagendar a mesma operação lógica com a mesma chave retorna o evento original.

## Cancellation

`pending` ou `claimed` podem ser cancelados.

Cancelamento:

- é idempotente;
- invalida lease atual;
- impede claim futuro;
- impede conclusão pelo token anterior.

Evento `completed` não pode ser cancelado.

## Fora da fase

Ainda não entram:

- stale protection por `sequence_snapshot`;
- follow-up;
- inactivity;
- execução automática de handlers;
- retry automático de side effects;
- integração do scheduler com regras clínicas.
