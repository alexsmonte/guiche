# Guichê v1.3.0 — Fase 04 — External Adapters / Chatwoot

## Baseline

- branch: `feature/v1.3.0-contexto-externo-confiavel`
- parent esperado: `fffd3f4acc7de2af2e7c42a215ce0f5fe391504b`

## Objetivo

Provar a integração de uma aplicação externa com o fluxo:

```text
Chatwoot
→ host confiável
→ adapter
→ bindIdentity()
→ TenantResolver
→ tenant_id
→ handle()
```

sem adicionar dependência Chatwoot ao Core.

## Decisão arquitetural

O adapter fica em:

```text
examples/chatwoot/
```

e não em:

```text
src/
```

O Core conhece apenas identity, session, TenantResolver e Tools.

## Identity de referência

```text
provider=chatwoot
account_id
inbox_id
conversation_id
```

O ID da mensagem não participa da identity.

## Session ID

A session ID é determinística por conversa e opaca:

```text
chatwoot-<sha256(provider:account:inbox:conversation)>
```

## Fronteira de confiança

O adapter recebe somente `trustedPayload`.

Ele não afirma nem tenta inventar autenticação do webhook.

A aplicação hospedeira precisa autenticar/validar o request antes de
promovê-lo a payload confiável.

## Segurança

O adapter falha fechado para:

- evento diferente de `message_created`;
- mensagem não incoming;
- mensagem privada;
- IDs ausentes/inválidos;
- divergência `inbox.id` x `conversation.inbox_id`;
- divergência `account.id` x `conversation.account_id`;
- mensagem textual vazia.

## Critérios de aceite

- duas mensagens da mesma conversa usam a mesma identity/session;
- conversas diferentes usam sessions diferentes;
- o adapter chama `Guiche::bindIdentity()`, nunca `ExecutionContextSeeder`;
- tenant é resolvido antes de `handle()`;
- segunda mensagem não exige nova resolução de tenant já persistido;
- nenhum símbolo Chatwoot entra em `src/`;
- API freeze permanece intacto;
- `composer84 check` verde;
- commit local apenas.
