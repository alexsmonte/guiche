# Guichê v0.5.1 — Fase 06 / Stale Protection + Follow-up + Recovery

## Fluxo

```text
resposta concluída
      ↓
FollowUpScheduler
      ↓
ScheduledEvent
  sequence_snapshot=N
  required_state={}
      ↓
due_at
      ↓
claim + lease
      ↓
revalidação da conversa
      ├── sequence != N → stale
      ├── state mudou   → stale
      └── válido        → handler
                            ├── sucesso → completed
                            └── exceção → indeterminate
```

## Follow-up inicial

Default:

```text
300 segundos / 5 minutos
```

É configurável.

O Core não define texto, canal ou regra clínica do follow-up.

## Stale protection

`FollowUpScheduler` captura `conversation.sequence` no momento do agendamento.

`ScheduledEventRunner` revalida esse snapshot imediatamente antes do handler.

Para a mesma conversa, a revalidação e o handler ficam dentro do lock do
`ConversationStore`, portanto um `IncomingEvent` concorrente não pode
incrementar a sequence entre o último stale-check e o início da execução.

## Required state

Precondições são genéricas:

```php
[
    'state.stage' => 'waiting',
]
```

Nenhum estágio clínico é conhecido pelo Core.

Mudança de estado torna o evento `stale`.

## Indeterminate

Depois que o handler começou, qualquer exceção é tratada conservadoramente como:

```text
indeterminate
```

Persistimos somente:

```text
failure_class
```

A mensagem da exceção não é persistida.

`indeterminate` é terminal e não volta para a fila automaticamente.

## Recovery

- `pending` sobrevive a restart;
- lease expirado antes do handler pode ser reclaimed;
- `completed`, `stale`, `cancelled` e `indeterminate` não são reclaimed;
- nenhum retry cego é feito depois de execução potencialmente externa.

## Fora da fase

A Fase 06 não contém regras clínicas.

Integração específica de domínio continua fora do Core.
