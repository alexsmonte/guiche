# Guichê v1.1.0 — Fase 05 — Clinical Example Multi-tenant

Fluxo:

```text
session
  ↓
execution_context.identity
  ↓
TenantResolver
  ↓
execution_context.tenant_id
  ↓
ToolExecutionContext
  ↓
Tool clínica
  ↓
empresa_id confiável
```

As cinco Tools clínicas agora implementam
`ContextAwareToolInterface`.

`empresa_id` não faz parte do schema enviado à IA. No caminho
contextual a empresa é obtida de `ToolExecutionContext::tenantId()`.

`ConsultarPaciente` usa também `ToolExecutionContext::sessionId()`.

`ClinicalSlotRevalidator` não guarda mais uma empresa fixa: recebe o
tenant da execução atual antes da WRITE.

`agent_context` não contém mais `empresa_id`. O piloto usa
`tenant_context.default_key` + `tenant_context.tenants`.

Exemplo:

```bash
export GUICHE_CLINIC_TENANT_MAP='{"clinica-a":101,"clinica-b":202}'
php examples/clinica-piloto/chat.php sessao-a clinica-a
php examples/clinica-piloto/chat.php sessao-b clinica-b
```

Compatibilidade mantida:

- `execute()` legado;
- fake-smoke;
- Gate 1;
- Gate 2;
- READ cache;
- WRITE replay/idempotência;
- Result Projection;
- ToolPolicy;
- Completion Guards.

Próxima fase: isolamento adversarial, identity swap, tenant ausente,
tenant forjado, concorrência e regressão de Tools legadas.


## Compatibilidade do ClinicalSlotRevalidator

Para preservar consumidores anteriores do exemplo clínico, o construtor
mantém o `companyId` legado como fallback opcional e `revalidate()`
continua podendo ser chamado somente com `$arguments`.

No runtime contextual v1.1, `CriarAgendamentoTool::executeWithContext()`
injeta `empresa_id` a partir de `ToolExecutionContext::tenantId()` e
`revalidate($arguments, $companyIdConfiavel)` sobrescreve o fallback.

O `ClinicPlugin` registra o revalidator com fallback `0`, portanto o
caminho normal do piloto v1.1 não possui tenant fixo em configuração.
