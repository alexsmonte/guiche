# Guichê v1.6.0 — Fase 02: Operational State

## Decisão

A v1.5 já possui `ClinicStateManager`.

A v1.6 não cria um segundo `AtendimentoStateManager` paralelo. A implementação
existente é evoluída preservando o contrato e o fluxo clínico publicado.

## Mapeamento do documento para o estado existente

| Documento | Estado clínico existente |
|---|---|
| tipo de atendimento | `context.intent` |
| convênio | `state.convenio.nome` |
| serviço | `state.procedimento` |
| profissional | `state.profissional` |
| período | `state.data_inicio/data_final` |
| data escolhida | `state.data_agendamento` |
| hora escolhida | `state.horario` |
| CPF | `state.cpf` |
| paciente | `state.paciente_id/paciente_nome` |
| agendamento | `state.agendamento_id` |
| status operacional | `state.etapa` |

Não foi criado `state.atendimento` em paralelo porque isso produziria duas
fontes de verdade para o mesmo fluxo.

## Entregue

- `quero marcar/agendar` pode registrar `intent=agendamento`;
- `reagendar/remarcar` registra `intent=reagendamento`;
- `cancelar/desmarcar` registra `intent=cancelamento`;
- `particular`, `sem convênio` e `não tenho convênio` registram Particular;
- nenhuma mensagem do usuário inventa IDs;
- troca explícita de convênio invalida escolhas dependentes;
- `ConsultarHorarios` aceita `data_inicio` e `data_inicial`;
- transições clínicas existentes permanecem intactas;
- falha de Tool continua sem produzir patch.

## Adiado deliberadamente para a Fase 03

A interoperabilidade operacional fica separada do StateManager básico:

- `CadastrarPaciente`;
- `ConsultaPaciente` x `ConsultarPaciente`;
- `AgendarConsulta` x `CriarAgendamento`;
- formatos reais/legados de retorno dessas Tools.

Assim a Fase 02 permanece focada em estado e a Fase 03 em operações externas.
