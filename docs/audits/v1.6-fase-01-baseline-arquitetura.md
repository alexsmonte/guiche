## Decisão arquitetural

A v1.6 **não colocará regras de atendimento clínico no Core genérico**.

O `AtendimentoStateManager` é uma implementação de domínio/aplicação. Ele deverá viver no
exemplo/consumidor clínico apropriado e usar os contratos genéricos do Guichê.

O Core só será alterado nas fases em que o backlog exigir capacidade genérica nova,
por exemplo:

- Trusted Parameter Binding;
- Session TTL;
- detecção de primeira mensagem/sessão;
- suporte necessário ao follow-up;
- composição de múltiplos prompts, se a API atual não for suficiente;
- DX declarativa para múltiplas Tools, se ainda houver lacuna.

## Descobertas do baseline real

A auditoria da v1.5 mostrou que parte do backlog já existe e não deve ser
reimplementada:

- `ClinicStateManager` já existe em `examples/clinica-piloto/`;
- `CriarAgendamentoTool` já existe com Safety Layer e idempotência;
- cache/reuso de Tools READ já existe e produz `tool_cache_hit`;
- Conversation Runtime já possui scheduler, follow-up, stale protection e recovery;
- `GuicheBuilder::loadTools()` e `$app['tools']` com strings já existem.

A v1.6 deve evoluir essas capacidades, não duplicá-las.

## Plano revisado da v1.6.0

1. Baseline + arquitetura + gap analysis.
2. Operational State: evoluir o `ClinicStateManager` existente.
3. Operações clínicas/interoperabilidade: `CadastrarPaciente` e compatibilidade
   `AgendarConsulta`/`CriarAgendamento`.
4. Trusted Parameter Binding.
5. Reusable Tools: validade e invalidação segura do cache READ.
6. Session Lifecycle: TTL + primeira mensagem de sessão nova/expirada.
7. Follow-up DX: configuração e integração da infraestrutura já existente.
8. Multiple Prompts: composição declarativa de vários prompts.
9. Declarative Loading DX: consolidar Tools/Plugins/StateManager no consumidor.
10. Acceptance real, instalação consumidora, documentação e release `v1.6.0`.

Nenhum requisito foi descartado. Recursos já presentes mudaram de
“implementar do zero” para “validar, evoluir e integrar”.

## Regra de avanço

Cada fase deverá cumprir:

```text
implementação
→ testes focados
→ composer84 check
→ compatibilidade/API quando aplicável
→ acceptance da fase
→ commit local
→ próxima fase
```

Nenhuma fase deve fazer push, merge ou tag antes do acceptance final da v1.6.0.
