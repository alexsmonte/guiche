# Guichê v1.3.0 — Fase 05 — Concurrency + Regression + DX

## Baseline

- branch: `feature/v1.3.0-contexto-externo-confiavel`
- parent esperado: `c5d61606e3dc484ff01861d40126db5972f24748`

## Problema fechado

`handle()` já era serializado por sessão, mas `bindIdentity()` ainda podia
correr em paralelo com um turno da mesma sessão.

A Fase 05 coloca `bindIdentity()` no mesmo lock exclusivo por sessão usado
por `handle()`.

Nenhuma assinatura pública é alterada.

## Propriedades testadas

### Mesma identity, mesma sessão

Múltiplos processos podem fazer o mesmo binding concorrentemente.

Resultado esperado:

```text
todos idempotentes
identity única
tenant único
nenhuma corrupção
```

### Identities conflitantes

Dois processos tentam identidades diferentes na mesma sessão.

Resultado:

```text
um vence
outro falha fechado
identity/tenant persistidos permanecem consistentes
```

### bindIdentity() x handle()

Um resolver é deliberadamente mantido aberto enquanto outro processo tenta
executar `handle()` na mesma sessão.

O `handle()` precisa aguardar o binding terminar.

Isso impede que um turno atravesse a fronteira de inicialização confiável da
sessão.

### Sessões diferentes

Locks permanecem por sessão.

Uma sessão bloqueada não pode bloquear outra sessão independente.

## DX

Exemplos possíveis incluem CRM próprio, Telegram, Instagram, WhatsApp Cloud

confiável.

## Compatibilidade

- `Guiche::bindIdentity()` mantém assinatura;
- `Guiche::handle()` mantém assinatura;
- `ToolInterface` permanece intacta;
- Safety Layer permanece intacta;
- API freeze v1 deve permanecer idêntico.

## Critérios de aceite

1. mesmo binding concorrente é idempotente;
2. binding conflitante falha fechado;
3. bind e handle da mesma sessão são serializados;
4. sessões diferentes não compartilham lock;
5. identity/tenant não sofrem corrupção;
6. exemplo genérico não usa `ExecutionContextSeeder`;
7. testes v1.3 anteriores continuam verdes;
8. `composer84 check` verde;
9. API freeze preservado;
10. commit local apenas.
