> Documento de implementação do exemplo clínico avançado do Guichê v1.

**Versão do documento:** 1.0
**Fase:** `v0.8.0 — Clinical Example`
**Projeto:** Guichê
**Pacote:** `asmpkg/guiche`
**Baseline esperado:** `v0.7.0 — Developer Experience`
**Documento-pai:** `DOCUMENTO_MAE_GUICHE_V1.md`
**Roadmap:** `ROADMAP_DESENVOLVIMENTO_GUICHE_V1.md`
**Documento anterior:** `v0.7-developer-experience.md`

---

# 1. Objetivo desta fase

A `v0.8.0 — Clinical Example` tem como objetivo preservar o caso real que originou o Guichê como um **exemplo avançado completo**, sem reintroduzir dependências clínicas no Core.

A transformação desejada é:

```text
Core genérico
    +
Basic Example
    +
Clinical Example avançado
```

O exemplo clínico deve demonstrar, de forma concreta, que o Guichê suporta:

```text
fluxo complexo
state machine
múltiplas Tools
Tool Policy
presenters
read + write
preconditions
idempotência
revalidação antes de write
```

sem exigir qualquer mudança em `src/` para acomodar regras clínicas.

---

# 2. Critério central de conclusão

A fase está concluída quando:

> O piloto clínico funciona como exemplo/plugin avançado, separado do Core, demonstrando fluxo real de agendamento com estado, Tools, políticas, presenters, read/write, preconditions e idempotência.

E também quando:

```text
Core não depende do exemplo clínico
```

```text

        ↓

```


# 11. ClinicPlugin

O `ClinicPlugin` deve ser a porta de entrada do domínio clínico.

Responsabilidades:

```text
registrar StateManager
registrar Tools
registrar Presenters
registrar policies
registrar instruction fragments
registrar completion guards
registrar result projections
registrar hooks/preconditions clínicas
```

Não deve:

```text
editar Core
usar globais ocultas
depender de caminhos internos rígidos
carregar segredo hardcoded
```

Pode conhecer:


# 14. Regra de invalidação

Mudanças de contexto clínico devem invalidar estados dependentes.

Exemplos:

```text
mudou convênio
→ invalidar procedimento/profissional/horário posteriores quando necessário

mudou procedimento
→ recalcular profissionais válidos

mudou profissional
→ invalidar período/horário escolhido

mudou data/período
→ invalidar horário
```

Essa regra pertence ao `ClinicStateManager` ou componentes clínicos equivalentes.

# 28. Result Projection

Tools clínicas devem usar projeção para evitar enviar dados desnecessários à IA.

```text
raw_result
├── dados internos
├── campos técnicos
├── informações sensíveis
└── campos necessários para conversa
        ↓
projection
        ↓
ai_result
```

---

# 29. Dados sensíveis

Não enviar à IA automaticamente:

```text
CPF completo
token
headers
senha
payload bruto de API
dados internos desnecessários
```

A projeção deve ser explícita.

# 30. Tool Policy clínica

A policy deve refletir o fluxo.

Exemplo conceitual:

```text
DisponibilidadeConvenios
→ permitido após convênio + procedimento

ConsultarProfissional
→ permitido após seleção válida

ConsultarHorarios
→ permitido após profissional

ConsultarPaciente
→ permitido antes de write

CriarAgendamento
→ somente em ready_to_create
```

A regra exata deve refletir o fluxo real existente.

---

# 31. Ordem clínica obrigatória

O exemplo pode demonstrar ordem semelhante a:

```text
CONVÊNIO
    ↓
PROCEDIMENTO
    ↓
PROFISSIONAL
    ↓
PERÍODO/DATA
    ↓
HORÁRIO
    ↓
PACIENTE
    ↓
CONFIRMAÇÃO
    ↓
WRITE
```

O estado e a Tool Policy devem garantir essa ordem.


```text

remarcação automática completa
```

# 34. Comportamento esperado

```text
paciente encontrado
        +
agendamento existente
        ↓
mensagem determinística
        ↓
usuário decide
        ↓
continuar novo agendamento?
        ↓
sim → prosseguir
não → encerrar/preservar existente
```

---

# 35. Preservar slot solicitado

Se a decisão sobre agendamento existente ocorrer após seleção de horário:

```text
não perder o slot solicitado
```

salvo se ele precisar ser revalidado e já não estiver disponível.

---

# 36. Slot Revalidation

O Roadmap exige revalidar disponibilidade antes do write.

```text
horário escolhido
        ↓
usuário confirma
        ↓
antes de CriarAgendamento
        ↓
revalidar slot
        ↓
disponível?
  SIM → execute write
  NÃO → bloquear write
         voltar para escolha
```

---

# 37. Por que revalidar

Entre consulta e criação do agendamento, outro processo pode ocupar o horário.

A escolha anterior não é garantia de disponibilidade atual.

---

# 38. Precondition hook

O Core deve permitir hook/precondition genérico.

O exemplo clínico registra algo equivalente a:

```php
beforeExecute(
    tool: 'CriarAgendamento',
    callback: $revalidateSlot
);
```

ou API equivalente já disponível.

---

# 39. Falha de revalidação

Se o slot não estiver mais disponível:

```text
CriarAgendamento NÃO executa
```

O state clínico deve voltar para uma etapa segura, como:

```text
waiting_time
```

ou equivalente.

---

# 40. Mensagem determinística de slot indisponível

O usuário deve receber mensagem baseada em fato real.

```text
Esse horário não está mais disponível.
Escolha outro horário.
```

Não afirmar criação.

---

# 41. Write idempotente

`CriarAgendamentoTool` deve usar a proteção genérica da Safety Layer.

Repetição idêntica:

```text
mesma sessão
mesma Tool
mesmos argumentos
```

não deve criar dois agendamentos.

---

# 42. Evidência de sucesso

O write deve retornar evidência concreta.

Exemplo:

```text

```

ou identificador equivalente.

Sem identificador/evidência válida:

```text
não afirmar sucesso
```
